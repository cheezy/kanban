# Stride for iOS and iPadOS

The rules in [../CLAUDE.md](../CLAUDE.md) apply here too. This file adds the
iOS and iPadOS ones. Section 12 of
[docs/plans/NATIVE-MOBILE-APPS-PHASE-1-DESIGN.md](../../docs/plans/NATIVE-MOBILE-APPS-PHASE-1-DESIGN.md)
has the platform choices behind them.

`project.yml` describes the `Stride` app, the `StrideKit` package, the
`StrideWidgets` and `StrideNotificationService` extensions, and the two test
targets. `mix mobile.strings` generates the app's string catalog,
`Stride/Resources/Localizable.xcstrings`. Nothing generates the asset-catalog
colours yet, so views use the system's own, such as `.primary` and `.background`;
add the first colour with that generator, not by hand. The asset catalog,
`Stride/Resources/Images.xcassets`, holds only the logo tile so far, named in
Swift through its generated symbol as `Image(.strideLogoTile)`. The app shows the
Update required screen, then the Sign in screen until the device is signed in,
then a placeholder, and the widget's view is a placeholder. The
widget shows no text, because the catalog is in the app alone.

- **Support both themes.** Use the generated asset-catalog colours, which carry a light and a dark value, and check every screen in both appearances before you finish.
- **Support iPhone and iPad.** Every screen looks right on both. Lay out by the available width, not the device, so an iPad in a narrow split view gets the phone layout: `TabView` in a compact width, `NavigationSplitView` in a regular one, and text kept to a readable width instead of stretched across the screen. Before you finish, run the tests on an iPad as well (`MIX_ENV=test mix ios.test --simulator "iPad (A16)"`) and look at every screen you changed on one, upright and on its side, in both appearances and at the largest text size.
- **Ship all seven locales.** Show every string through the Xcode string catalog generated from the `mobile` gettext domain, in de, en, es, fr, ja, pt and zh. Check layouts at the largest text size in German, where labels run longest. Xcode makes a Swift symbol of each string, so `update_required_title` is `Text(.updateRequiredTitle)`, and `LocalizationTests` fails when the app lacks a locale or its text. The catalog leaves out plurals and strings with a placeholder: extend `Kanban.Mobile.StringCatalog` before a screen needs one, and never edit the catalog in Xcode.
- **Label everything for accessibility.** Give every control a VoiceOver label, support Dynamic Type up to the accessibility sizes, keep touch targets at least 44 points, and run `performAccessibilityAudit()` in the UI tests. Ignore an audit issue only for elements named by an accessibility identifier, with the reason beside it, as `SignInUITests` does for the points' text.
- **Keep business logic out of views.** SwiftUI views render `@Observable` view models and nothing more. The API client, auth, cache, live channel and push registration belong in `StrideKit`, which the app and its extensions share, and view models depend on protocols so previews and tests run against `mobile/shared/fixtures/`.
- **Regenerate after changing a source.** After the API contract changes, run `mix mobile.api` to check it and refresh `StrideKit/Sources/StrideKit/openapi.json`, which the Swift OpenAPI Generator build plugin turns into the Swift client (`openapi-generator-config.yaml` beside it picks the operations). When the client lacks or refuses something, change the contract, or the derivation in `lib/kanban/mobile/swift_contract.ex`; after the tokens or strings change, run `mix mobile.tokens` or `mix mobile.strings`. Never edit generated files by hand.
- **Reach the API through `StrideAPI`.** The app takes its one client from `StrideApp.api`, which `APIClient.make` builds. It sends only to the Stride server, follows no redirect, reports the app's version with every request, sends the device's access token, refreshes that once when the server answers 401, and repeats a read once when the server is restarting. Never build a `Client` or a `URLSession`, nor a second `APIClient`: two would refresh the same token twice, and the server revokes the device for that. An extension must not use it, because a refresh writes to `AuthStore`. A call that fails throws a `ClientError` whose `underlyingError` is an `APIClientError`, an `AuthStoreError` or a `URLError`, or another error when the call was cancelled or its answer could not be decoded; only `APIClientError.signedOut` means that the sign-in is over, and `AuthStore` announces a refused one through `signedIn`. Previews and tests use `FixtureAPI().client`, which answers from `mobile/shared/fixtures/` through the same generated decoding and exists only in debug builds, so wrap a preview that uses it in `#if DEBUG`. To show a response the fixtures lack, replace its body in the test; the shared fixtures hold one example per operation whose success response has a JSON body. Never log or show a `ClientError`, an input or an output: each holds the request or response, with any token in it.
- **Keep device tokens in `AuthStore`.** It holds the token pair as one Keychain item in the shared access group, and nothing else may store, log, print or snapshot a token; `TokenPair` prints as `TokenPair(redacted)`. Use `StrideApp.authStore` in the app. After a sign-in call `save(_:approvalKey:)`, which keeps the approval key as a second item of the same service, and on sign-out `clear`, which removes both; the client rotates the pair after a refresh and clears it when the server refuses one. Only the app writes and extensions only read, since two writers could overwrite each other's pair. Tell `AuthStoreError.keychain` from a nil read: nil means signed out, while the Keychain refuses every read until the device is first unlocked after a restart. Keep the `install-marker` file in the app group container: while it is missing, reads are nil and the app clears what a previous install left.
- **Sign in through `SignInModel`.** The Sign in screen opens the web's `/oauth/authorize` page in `ASWebAuthenticationSession` with a new `OAuthAttempt` for each press, so each try has its own PKCE verifier and state, checks the callback's state, and trades the code once through `OAuthFlow.exchange`. Never repeat the exchange: the server burns a code it refuses, and `APIClient` repeats only reads. The approval key is made before the browser opens, in the Secure Enclave on a device; the exchange sends its public half and `AuthStore` keeps its handle. When `/api/me` says the plan does not include the app, the screen shows the locked panel, keeps the sign-in and asks again each time the app becomes active. Start a debug build with `-StrideStubSignIn` followed by `allow`, `cancel`, `locked` or `offline` to sign in through a stub browser, the fixtures and a store in memory. [docs/ios-sign-in.md](../../docs/ios-sign-in.md) has each step.
- **Leave an outdated app to `AppUpdateState`.** When the server answers 426, the client sets `StrideApp.update` and `RootView` shows the Update required screen until the app is updated and started again, so no view model handles 426. The link is the `store_url` the server sends when that is a page of Apple's, and the app's own page otherwise. Start a debug build with the `-StrideUpdateRequired` argument to see the screen.
- **Pin every Swift package.** `StrideKit/Package.swift` names exact versions and `Package.resolved` pins what those depend on; `xcodegen generate` copies it into the project. To change a version, edit `Package.swift`, generate, resolve in Xcode or `xcodebuild -resolvePackageDependencies`, copy the project's `Package.resolved` back to `mobile/ios/` and commit both. Because the generator is a build plugin, every `xcodebuild` call that builds needs `-skipPackagePluginValidation`; the two mix tasks and `ios.yml` pass it.
- **Never commit the Xcode project.** The `.xcodeproj` is generated from `project.yml` and is ignored; change `project.yml` instead and run `xcodegen generate`. Build output, `DerivedData` and per-user Xcode state are ignored too.
- **Build and test with the mix tasks.** From the repository root, `MIX_ENV=test mix ios.test` runs the tests and shows each result, and `MIX_ENV=test mix ios.deploy` builds the app and starts it on a simulator. Each generates the project first and keeps the full log in `build/`. [docs/ios-mix-tasks.md](../../docs/ios-mix-tasks.md) has the options.
- **Use the iOS Stride hooks.** `./ios_dev.sh` at the repository root switches the Stride hooks to the set for this app: `mix ios.test` runs the `Stride` scheme on a simulator and `test/ios_elixir_checks.sh` runs the Elixir tests that read `mobile/` before each task commit. [docs/hook-time-budget.md](../../docs/hook-time-budget.md) describes it, and `./stride_dev.sh` switches back.
- **Never commit signing material.** Certificates (`.p12`), App Store Connect keys (`.p8`) and provisioning profiles stay out of the repository.
- **Keep one copy of each identifier.** `project.yml` sets `STRIDE_BUNDLE_ID`, and the bundle ids, the app group and the keychain access group come from it as build settings. The entitlements grant both groups and each Info.plist names them, so Swift code reads them through StrideKit's `AppGroup` instead of repeating them. A new extension that shares data needs the same two entitlements and the same two Info.plist keys, and `EntitlementsTests` must list it.
- **Enable only the entitlements Phase 1 needs.** The app has the app group, the keychain access group, push and associated domains; the extensions have only the two groups. `EntitlementsTests` fails when a target gains another.
- **Keep the names CI uses.** [ios.yml](../../.github/workflows/ios.yml) generates `Stride.xcodeproj` from `project.yml` and tests the `Stride` scheme on an iPhone and an iPad simulator. It runs Swift Testing in `StrideTests` and in the StrideKit package's `StrideKitTests`, the snapshot tests in the `SnapshotTests` suite of `StrideTests`, and XCUITest in `StrideUITests`. All three targets must be in the `Stride` scheme's test action in `project.yml` (list the package's as `package: StrideKit/StrideKitTests`): naming a target the scheme lacks fails the run. It pins the Xcode version, the simulator OS and XcodeGen in its `env` block; change them there.
