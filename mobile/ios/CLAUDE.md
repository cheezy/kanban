# Stride for iOS and iPadOS

The rules in [../CLAUDE.md](../CLAUDE.md) apply here too. This file adds the
iOS and iPadOS ones. Section 12 of
[docs/plans/NATIVE-MOBILE-APPS-PHASE-1-DESIGN.md](../../docs/plans/NATIVE-MOBILE-APPS-PHASE-1-DESIGN.md)
has the platform choices behind them. Before any change here, load the project
skill `stride-ios` (`.claude/skills/stride-ios/SKILL.md`) with the Swift skills:
it holds the commands, simulators, design facts and past failures that these
rules leave out. When a task teaches something new about working on this app,
add it to that skill in the same task.

`project.yml` describes the `Stride` app, the `StrideKit` package, the
`StrideWidgets` and `StrideNotificationService` extensions, and the two test
targets. `mix mobile.strings` generates the app's string catalog,
`Stride/Resources/Localizable.xcstrings`. `mix mobile.tokens` generates the
colour catalog, `Stride/DesignSystem/Colors.xcassets`, with a light and a dark
value for every Stride colour token, and `Stride/DesignSystem/DesignTokens.swift`
with the font families, the text styles and the radii. Name a colour through the symbol
Xcode makes of it, so the token `ink-2` is `Color(.ink2)`, and show text in a
`StrideTextStyle` with `.textStyle(.body)`: each style is in Geist or Geist Mono
and scales with Dynamic Type. The Sign in and Update required screens still use
the system's colours and fonts, such as `.primary` and `.headline`; move a screen
to the tokens when you next change it. The image catalog,
`Stride/Resources/Images.xcassets`, holds only the logo tile so far, named in
Swift through its generated symbol as `Image(.strideLogoTile)`. The app shows the
Update required screen, then the Sign in screen until the device is signed in,
then the shell, whose Now tab shows the decisions waiting on the person, with
each card's buttons, whose Review tab shows the pending reviews in the
server's order and opens each one's review screen, and from it each changed
file's read-only diff screen, and whose Boards and Agents tabs show only their titles so far,
and the widget's
view is a placeholder. The
widget shows no text, because the catalog is in the app alone.

- **Support both themes.** Use the generated asset-catalog colours, which carry a light and a dark value, and never a colour or a font written in Swift. Check every screen in both appearances before you finish. `DesignTokenTests` fails when an asset differs from `mobile/shared/tokens/tokens.json` or a pair of tokens falls below its contrast floor.
- **Support iPhone and iPad.** Every screen looks right on both. Lay out by the available width, not the device, so an iPad in a narrow split view gets the phone layout: `TabView` in a compact width, `NavigationSplitView` in a regular one, and text kept to a readable width instead of stretched across the screen. Before you finish, run the tests on an iPad as well (`MIX_ENV=test mix ios.test --simulator "iPad (A16)"`) and look at every screen you changed on one, upright and on its side, in both appearances and at the largest text size.
- **Ship all seven locales.** Show every string through the Xcode string catalog generated from the `mobile` gettext domain, in de, en, es, fr, ja, pt and zh. Check layouts at the largest text size in German, where labels run longest. Xcode makes a Swift symbol of each string, so `update_required_title` is `Text(.updateRequiredTitle)`. A string with arguments, such as a plural, goes through its accessor in `Stride/DesignSystem/L10n.swift`, which `mix mobile.strings` generates with each argument named after its placeholder: `Text(.targetTaskProgress(done: 2, count: 5))`, never Xcode's unlabelled `.targetTaskProgress(_:count:)`. The catalog turns each `{name}` into a positional specifier, so a translation may reorder the arguments, and varies each plural by `count`. Pass only values to an accessor, never server text as the format. Text iOS shows from the Info.plist, such as Face ID's reason, is a `mobile` string too: `mix mobile.strings` writes it to `Stride/Resources/InfoPlist.xcstrings` under its Info.plist key (`Kanban.Mobile.InfoPlistCatalog`), and `project.yml` sets the key's English value (`INFOPLIST_KEY_NSFaceIDUsageDescription`), since iOS reads only a key the Info.plist has. Without that key Face ID is refused to the app. `LocalizationTests` fails when the app lacks a locale, a key or its text, or a placeholder or plural form renders wrongly. Never edit the catalog or the accessors in Xcode.
- **Label everything for accessibility.** Give every control a VoiceOver label, support Dynamic Type up to the accessibility sizes, keep touch targets at least 44 points, and audit every screen in the UI tests with `app.auditAccessibility()`, which runs the contrast check of `performAccessibilityAudit` on its own and first, before the checks that resize the text and scroll the screen. Ignore an audit issue only for elements named by an accessibility identifier, with the reason beside it, as `SignInUITests` does for the points' text. The one exception is the iPad's form sheet, which leaves the screen behind it dimmed and out of VoiceOver's reach: `ShellUITests` ignores the "potentially inaccessible text" issue with no element there, on an iPad only. `ShellUITests`, `NowUITests` and `ReviewUITests` also ignore the contrast issue on an iPad sidebar row's title (`sidebar-tab-title`) and its Now count (`sidebar-count`), `isOnSidebarRow`, and on a decision card's or a Review queue row's mono identifier and age (`card-identifier`, `card-age`), `isOnCardMonoText`: the audit fails one or another from run to run, on iOS 27 upright and on its side and on iOS 26 in dark, though `SharedViewAccessibilityTests` holds their token pairs to 4.5:1 in both themes. `NowUITests`, `ShellUITests` and `ReviewUITests` also ignore a contrast issue on an element that cannot be hit inside the Now cards or the Review rows, or that reaches or scrolls under the tab bar, a navigation bar or a pinned bottom bar of buttons (`review-bottom-bar`, `diff-bottom-bar`), or past the top edge, where it is faded or covered on purpose (`isUnderBarsContrast` in `AccessibilityAudit.swift`); `DiffUITests` uses it too. `NowUITests` and `ShellUITests` also ignore a contrast issue on a Now filter's count (`isOnNowFilterCount`), which an iPad's audit fails from a tiny crop of the thin digit though the count reaches 5:1. Before iOS 26, `ShellUITests`' largest-text German test also ignores a clipped-text issue on a Now filter's label (`now-filter-label`, `isNowFilterLabelClippedBeforeIOS26`): the iOS 17 and 18 audit fails the medium-weight "Prüfungen" in the variable Geist font though the whole word shows with room to spare, and passes it at the regular weight. `ShellUITests`' test of each tab ignores a Dynamic Type issue on a Now card or a Review queue row after the first (`isOnLazyCard`): the audit's larger text pushes them off the screen and the lazy list lets go of them. Its largest-text German test audits them without that filter, since there is no larger size to push them off with. `ReviewUITests` ignores a clipped-text or Dynamic Type issue on text in a review section that reaches under the review screen's bottom bar (`isUnderReviewBottomBar`), which covers the end of the scrolled content as the tab bar does: the audit's larger text pushes the rest of that section under the bar, though it reports the text's frame at the normal size. It also ignores a contrast issue inside the review's acceptance tile (`review-criteria-tile`, `isOnCriteriaTile`), whose short mono criteria count an iPad's audit fails from a tight crop though `SharedViewAccessibilityTests` holds every verdict pair to 4.5:1. On iOS 26 only (not 27, not before 26), it ignores a contrast issue inside the review's bottom bar, its header's agent and details line or its "Flagged first" line, or on a section's heading (`review-bottom-bar`, `review-details`, `review-flagged-first`, `review-section-heading`, `isOnReviewContrastMisjudgedOnIOS26`), which iOS 26.4 failed on every run though `SharedViewAccessibilityTests` holds their pairs to 4.5:1 and iOS 27 passes them; `DiffUITests` uses it too, for the file screen's bar (`diff-bottom-bar`). `DiffUITests` ignores the "not human-readable" issue on the diff screen's title, which is the file's name, only when the header's path reading names it (`isFileNameTitle`). It also ignores a contrast issue on the "flagged" pill (`diff-flagged`, `isOnFlaggedPill`) and, on an iPad only, on a line of the code (`diff-line`, `isOnDiffLineOnIPad`), not the notes between the lines, which the audit judges from a crop of a lone mono line number; `SharedViewAccessibilityTests` holds the pill's and every line's inks to 4.5:1, and the iPhones still audit the lines. A short glyph inside a combined accessibility element whose meaning the label already says, such as a diff line's + or − marker, shares a neighbouring text (`DiffLineContent.gutter(in:)`) rather than getting an audit filter: XCUI and the audit still reach a child under `.accessibilityElement(children: .ignore)`, and `.accessibilityHidden(true)` does not stop them. To audit a screen in both appearances, set the appearance and launch the app again before auditing, as `ReviewUITests` does, or the audit can read text that is still changing. Lay out text that must grow with an eager stack or `Grid`, or an `AnyLayout` chosen by `dynamicTypeSize.isAccessibilitySize`: the audit fails text in a `LazyVGrid` or a `ViewThatFits`, which let go of or swap a view as the text grows. At the accessibility text sizes, never pin a bar of buttons over a scrolled screen: put its buttons, stacked, at the end of the content, as `ReviewView` does, and stack a label that shares a row with an icon or a count, as `ReviewVerdictTile` does, and give a long path its own line, as `ReviewFileRowView` does, so no word breaks in the middle. Give a non-interactive accessibility element smaller than 44 points, such as a dot or a pill with its own label, the `.isStaticText` trait, so the audit does not hold it to a tap target's size. On a screen with screen-wide accessibility actions or a gesture, as the diff screen has for paging, also give each text that is not a control `.accessibilityRespondsToUserInteraction(false)`, or the audit holds every short text to 44 points (`DiffHeader`). Never put `.shadow` on a whole card or other container: SwiftUI then draws it under every text inside, and the audit fails their contrast; shadow the background shape instead, as `CardChrome` does.
- **Never hold up a scroll.** On iOS 18 and later, never attach a SwiftUI `DragGesture` inside a `ScrollView`, even a simultaneous one: it stops a fast flick that starts on it. Page sideways through a UIKit pan that begins only when the finger sets out mostly sideways, as `diffPagingSwipe` does (iOS 17, which lacks `UIGestureRecognizerRepresentable`, keeps the drag), and test it with a fast flick, as `DiffUITests` does.
- **Build screens from the shared views.** `Stride/DesignSystem/Views` holds the verdict and status pills, the priority dot, the agent avatar, the progress bar, the diff line, the offline banner, the decision and goal cards and the parts they share (`DecisionIdentifier`, `DecisionAge`, `DecisionAgentRow`, `VerdictFlow`), the loading, empty and nothing-saved states (`LoadingSkeleton`, `EmptyStateView`, `NothingSavedView`), and `PinnedBar`, which pins a bar of buttons under a scrolled screen. Put a view two features use here under a neutral name, never in one feature's folder under that feature's name. Each takes a plain value from `Stride/DesignSystem/Models`, which a view model makes from the API's values, says its state in words to VoiceOver, and shows the server's text as plain text, never as Markdown. Their colours are `ColorToken` cases, whose text inks `SharedViewAccessibilityTests` holds to 4.5:1 on their backgrounds in both themes; the dots, bar fills and borders are not checked. `Stride/Debug/SharedViewSamples.swift` holds the samples their previews and `SharedViewSnapshotTests` draw.
- **Keep business logic out of views.** SwiftUI views render `@Observable` view models and nothing more. The API client, auth, cache, live channel and push registration belong in `StrideKit`, which the app and its extensions share, and view models depend on protocols so previews and tests run against `mobile/shared/fixtures/`.
- **Regenerate after changing a source.** After the API contract changes, run `mix mobile.api` to check it and refresh `StrideKit/Sources/StrideKit/openapi.json`, which the Swift OpenAPI Generator build plugin turns into the Swift client (`openapi-generator-config.yaml` beside it picks the operations). When the client lacks or refuses something, change the contract, or the derivation in `lib/kanban/mobile/swift_contract.ex`; after the tokens or strings change, run `mix mobile.tokens` or `mix mobile.strings`. Never edit generated files by hand.
- **Reach the API through `StrideAPI`.** The app takes its one client from `StrideApp.api`, which `APIClient.make` builds. It sends only to the Stride server, follows no redirect, reports the app's version with every request, sends the device's access token, refreshes that once when the server answers 401, and repeats a read once when the server is restarting. Never build a `Client` or a `URLSession`, nor a second `APIClient`: two would refresh the same token twice, and the server revokes the device for that. An extension must not use it, because a refresh writes to `AuthStore`. A call that fails throws a `ClientError` whose `underlyingError` is an `APIClientError`, an `AuthStoreError` or a `URLError`, or another error when the call was cancelled or its answer could not be decoded; only `APIClientError.signedOut` means that the sign-in is over, and `AuthStore` announces a refused one through `signedIn`. Previews and tests use `FixtureAPI().client`, which answers from `mobile/shared/fixtures/` through the same generated decoding and exists only in debug builds, so wrap a preview that uses it in `#if DEBUG`. To show a response the fixtures lack, replace its body in the test, answer it with another status through `statuses`, or with a status chosen per call through `status:` (a 409 once, then the fixture), and hear what the client sent through `onSend`; the shared fixtures hold one example per operation whose success response has a JSON body. Never log or show a `ClientError`, an input or an output: each holds the request or response, with any token in it.
- **Keep device tokens in `AuthStore`.** It holds the token pair as one Keychain item in the shared access group, and nothing else may store, log, print or snapshot a token; `TokenPair` prints as `TokenPair(redacted)`. Use `StrideApp.authStore` in the app. After a sign-in call `save(_:approvalKey:)`, which keeps the approval key as a second item of the same service, and on sign-out `clear`, which removes both; the client rotates the pair after a refresh and clears it when the server refuses one. Only the app writes and extensions only read, since two writers could overwrite each other's pair. Tell `AuthStoreError.keychain` from a nil read: nil means signed out, while the Keychain refuses every read until the device is first unlocked after a restart. Keep the `install-marker` file in the app group container: while it is missing, reads are nil and the app clears what a previous install left.
- **Sign in through `SignInModel`.** The Sign in screen opens the web's `/oauth/authorize` page in `ASWebAuthenticationSession` with a new `OAuthAttempt` for each press, so each try has its own PKCE verifier and state, checks the callback's state, and trades the code once through `OAuthFlow.exchange`. Never repeat the exchange: the server burns a code it refuses, and `APIClient` repeats only reads. The approval key is made before the browser opens, in the Secure Enclave on a device; the exchange sends its public half and `AuthStore` keeps it with the biometric enrolment it was made under. When `/api/me` says the plan does not include the app, the screen shows the locked panel, keeps the sign-in and asks again each time the app becomes active. Start a debug build with `-StrideStubSignIn` followed by `allow`, `cancel`, `locked` or `offline` to sign in through a stub browser, the fixtures and a store in memory. [docs/ios-sign-in.md](../../docs/ios-sign-in.md) has each step.
- **Sign approvals through `ApprovalSigner`.** It signs the server's one-time challenge, with the task, `review_requested_at` and the decision bound in (`ApprovalPayload`, five lines the server builds the same way), after Face ID, Touch ID or the passcode, and answers `cancelled`, never an error, when the person closes the prompt. Pass the prompt's text in from the app ("Approve W2701"), since StrideKit has no strings. When there is no key, the enrolment has changed since sign-in or the Secure Enclave refuses the key, it has a new key made through `ApprovalKeyRegistering`, which is a new sign-in because only the token exchange carries a public key. Never sign anything but a challenge, and never log, print or snapshot the nonce, the key or the signature: `SignedApproval` and `ApprovalPayload` print as redacted. [docs/ios-approval-signer.md](../../docs/ios-approval-signer.md) has the details.
- **Cache through `Cache`.** `StrideApp.cache` keeps API responses in the app group container, each with its fetch time, which the offline banner shows. Read `epoch` before a request and pass it to `store(_:for:since:)`, so an answer that set out before a sign-out is dropped. Each kind's store and limit are in `CacheKind`, from the design's section 11; a new kind gets a case there and a `CacheKey`. Only the app stores and wipes. `SignInModel` wipes the cache whenever the device is signed out. Never cache a token. A change to the stored entry needs a new `VersionedSchema` in `CacheSchema.swift`. [docs/ios-cache.md](../../docs/ios-cache.md) has the details.
- **Receive live updates through `LiveChannel`.** `StrideApp.live` holds the one socket, which carries both `me:inbox` and `me:agents`; a view model reads `updates(of:)` for its topic and gets each channel's full state as the body of its API call, so it replaces what it shows rather than merging. Never open a second socket or name SwiftPhoenixClient outside `PhoenixConnection`. Every connect asks for a new single-use socket token, so never let the library reconnect by itself. A revoked device's socket closes like any other drop; the next token request finds the ended sign-in and `LiveChannel` clears `AuthStore`. `AppRouter.refresh()` calls `resume()` when the app becomes active. Never set the library's logger or log the socket URL, a push or a `SocketTokenAnswer`. [docs/ios-live-channel.md](../../docs/ios-live-channel.md) has the details.
- **Navigate through `AppRouter`.** `RootScreen` picks the window's screen and `AppShell` shows the four tabs, Now, Review, Boards and Agents, as a `TabView` in a compact width and a `NavigationSplitView` sidebar in a regular one, whose rows are buttons that draw their own selection in the design's `stride-orange-soft` and `stride-orange-ink`, because the list's own selection can put white text on the light dark-mode tint. `StrideApp` holds the one `AppRouter`, which keeps the selected tab, a path of `AppRoute`s per tab, the corner buttons' sheet and the Now badge; push a screen or open a deep link through its methods rather than a view's own `NavigationLink` state, so a sign-out can clear it all. Anything else the shell shows of the person must be cleared in `follow(_:)` too. [docs/ios-app-shell.md](../../docs/ios-app-shell.md) has the details.
- **Follow a Now card's buttons through `NowActions`.** `AppRouter` holds the one `NowActions`, which opens a review, a web page or the board's Backlog through the router, and moves a task to Backlog, opens the reply sheet (`ReplyModel`) and opens the View attempt sheet (`HookAttemptModel`) on the Now screen. Every action waits while the device is offline, and the buttons say they need a connection. A move takes the card off the list at once; a 409, a 404 or a `not_movable` refusal means the task moved first, so the notice says so and the list is fetched again. Open a web link only when `StrideWeb.isStridePage` passes it: https, the configured Stride host, no port and no user or password. The View attempt sheet shows a hook's exit code and duration and nothing else: the after_goal output can hold secrets or internal paths and never reaches the phone (decision 9 of the design). `AppRouter.follow(_:)` calls `NowActions.forget()`, so a sign-out drops an open sheet, a notice and an answer on its way.
- **Leave an outdated app to `AppUpdateState`.** When the server answers 426, the client sets `StrideApp.update` and `RootView` shows the Update required screen until the app is updated and started again, so no view model handles 426. The link is the `store_url` the server sends when that is a page of Apple's, and the app's own page otherwise. Start a debug build with the `-StrideUpdateRequired` argument to see the screen.
- **Pin every Swift package.** `StrideKit/Package.swift` names exact versions and `Package.resolved` pins what those depend on; `xcodegen generate` copies it into the project. To change a version, edit `Package.swift`, generate, resolve in Xcode or `xcodebuild -resolvePackageDependencies`, copy the project's `Package.resolved` back to `mobile/ios/` and commit both. Because the generator is a build plugin, every `xcodebuild` call that builds needs `-skipPackagePluginValidation`; the two mix tasks and `ios.yml` pass it.
- **Never commit the Xcode project.** The `.xcodeproj` is generated from `project.yml` and is ignored; change `project.yml` instead and run `xcodegen generate`. Build output, `DerivedData` and per-user Xcode state are ignored too.
- **Build and test with the mix tasks.** From the repository root, `MIX_ENV=test mix ios.test` runs the tests and shows each result, and `MIX_ENV=test mix ios.deploy` builds the app and starts it on a simulator. Each generates the project first and keeps the full log in `build/`. [docs/ios-mix-tasks.md](../../docs/ios-mix-tasks.md) has the options.
- **Use the iOS Stride hooks.** `./ios_dev.sh` at the repository root switches the Stride hooks to the set for this app: `mix ios.test` runs the `Stride` scheme on a simulator and `test/ios_elixir_checks.sh` runs the Elixir tests that read `mobile/` before each task commit. [docs/hook-time-budget.md](../../docs/hook-time-budget.md) describes it, and `./stride_dev.sh` switches back.
- **Never commit signing material.** Certificates (`.p12`), App Store Connect keys (`.p8`) and provisioning profiles stay out of the repository.
- **Keep one copy of each identifier.** `project.yml` sets `STRIDE_BUNDLE_ID`, and the bundle ids, the app group and the keychain access group come from it as build settings. The entitlements grant both groups and each Info.plist names them, so Swift code reads them through StrideKit's `AppGroup` instead of repeating them. A new extension that shares data needs the same two entitlements and the same two Info.plist keys, and `EntitlementsTests` must list it.
- **Enable only the entitlements Phase 1 needs.** The app has the app group, the keychain access group, push and associated domains; the extensions have only the two groups. `EntitlementsTests` fails when a target gains another.
- **Keep the names CI uses.** [ios.yml](../../.github/workflows/ios.yml) generates `Stride.xcodeproj` from `project.yml` and tests the `Stride` scheme on an iPhone and an iPad simulator. It runs Swift Testing in `StrideTests` and in the StrideKit package's `StrideKitTests`, the snapshot tests in the `SnapshotTests` and `SharedViewSnapshotTests` suites of `StrideTests`, and XCUITest in `StrideUITests`. All three targets must be in the `Stride` scheme's test action in `project.yml` (list the package's as `package: StrideKit/StrideKitTests`): naming a target the scheme lacks fails the run. It pins the Xcode version, the simulator OS and XcodeGen in its `env` block; change them there.
