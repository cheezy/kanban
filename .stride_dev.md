# Stride Configuration

**Note:** Examples below use Unix/Linux/macOS bash syntax. Windows users should see https://github.com/cheezy/kanban/blob/main/docs/WINDOWS-SETUP.md for PowerShell equivalents.

Trunk-based, two developers on SEPARATE clones (one agent per clone — never two
agents in one working tree). Each task is built on its own branch and merged into
LOCAL main only after it is approved. Commits accumulate on local main and are
pushed to origin ONLY when a goal completes (after_goal), after rebasing the
whole goal's worth of commits onto the latest origin/main and re-testing.
Standalone tasks (no parent goal) merge to local main but are NOT auto-pushed —
push those manually.

**Why `after_doing` runs `mix test` and not `mix test --cover` (D223).** The
hook budget is per SECTION — wall clock across all of a section's commands, not
per command. `after_doing`'s committed default was **120s** when this was
written; **D229 raised every section to 600s** (clamp 890s, `hooks.json` ceiling
900s), so the figures below are still accurate as durations but their "vs 120s"
column is historical.

With `--cover`, the section could never fit: `mix test --cover` measured **138s
on its own**, and the four gate commands totalled **152s**. The repo completed
tasks at all only because one machine carried an uncommitted
`STRIDE_HOOK_TIMEOUT_OVERRIDE=200` in `.claude/settings.local.json`. A fresh
clone could complete nothing.

**That override has now been REMOVED (D230).** It was retained deliberately
until D228 and D229 landed — `after_goal`'s 60s budget could not fit
`mix precommit`, and a cold clone could not clear `before_doing` at all. Both
have landed, so the last step of that sequence is done and
`.claude/settings.local.json` no longer carries an `env` block.

It mattered more than a leftover: at 200s it took **top precedence over the
600s default**, so this machine was running the gate at 200s against a measured
154s loaded section — **1.30x headroom, not the 3.9x the committed budget
provides**. D230's own no-change decision was very nearly made against that
wrong number. It would also have silently swallowed a re-added `--cover`
(152s < 200s), leaving the warning at the end of this section with no automated
backstop on the one machine that would have caught it. Both of those are now
gone: the gate here runs at the committed 600s.

Without it, measured with the override **unset**. Three consecutive warm runs
under `timeout 120` — the real committed budget, not a simulation — gave
**97s / 89s / 90s**, all passing. Then the same four commands were measured
per-command across three build states:

| State | `mix test` | format | credo | sobelow | **Section** | vs 120s |
|---|---|---|---|---|---|---|
| Warm, idle | 74s | 1s | 12s | 1s | **88s** | fits (best case) |
| Cold (`_build/test` wiped) | 172s | 2s | 13s | 2s | **189s** | **breaches by 69s** |
| Warm, 4 CPU burners | 149s (exit 2, see note) | 2s | 17s | 2s | **170s** | **breaches by 50s** |

**Quote the worst run, not the best.** Four warm-idle sections are now on record
— 88s, 89s, 90s and 97s. The table shows 88s because it is the run the
per-command breakdown came from, but **the planning margin is ~23s (120 − 97),
not 32s.** Size any future change against 97s.

**Read that honestly: the gate passes only when warm AND idle.** Dropping
`--cover` is a real improvement — the same section was 152s warm-idle before, so
it did not pass even there — but it does not make the gate reliable. `mix test`
is **84–91%** of the section in every state (74/88, 172/189, 149/170), so the
section's fate is essentially that one command's, and `after_doing` can only
choose which commands to run.

**On the historical 1.7× spread.** It is **superseded**, not explained: those
readings measured a gate containing `mix test --cover`, which no longer exists,
and the table above replaces them for all three states. Do not attribute that
variance to `--cover` — the numbers say otherwise. Warm-to-warm is only 1.09×,
while warm→cold is 2.1× and warm→loaded is 1.9×. **Build state and machine load
dominate; coverage was never the main variance term.**

The gate still blocks. Re-verified after the change: with a deliberately failing
test planted, the same section returns **exit 2**.

**Coverage enforcement moved, and it is now slower.** Nothing local checks
coverage any more — `mix precommit` runs plain `test`, not `test --cover`, so
`after_goal` does not cover either. CI runs `mix test --cover` against the 90%
threshold on push to `main`/`release` and PRs to `main`
(`.github/workflows/elixir.yml`), and `deploy-review`/`deploy-prod` both
`needs: test`, so a coverage failure blocks deploy. But this repo pushes only at
`after_goal`, and standalone tasks never auto-push — so a coverage regression
can survive locally for a whole goal before CI ever sees it. That is a real
trade, not a free one.

**On raising the budget instead.** The *server* timeout cannot help:
`after_doing` is routed at the PRE phase, where no response payload exists yet,
so it always resolves to the local default — which makes `lib/kanban/hooks.ex`'s
advertised timeout inert for this path. The local default in
`default_budget_for_section()` *is* editable, but that ships to every plugin
user rather than fixing this repo.

**That judgement was reversed by D229**, which raised the shared default
deliberately: the hook bodies became off-limits, removing every repo-local
lever, and a user without `jq` falls through to the same default anyway. Current
locations and values, replacing the pre-D229 citations that were here:
`default_budget_for_section()` at `stride/hooks/stride-hook.sh:1476-1485`
returns **600s** for every section, `resolve_section_budget()` clamps at
**890s** (`:1522`), and `hooks/hooks.json` carries a **900s** ceiling.

**What the two breaching rows mean, and where they are tracked.**

*Cold* costs a full `MIX_ENV=test` compile that `before_doing`'s `mix deps.get`
/ `mix ecto.migrate` (which compile `:dev`) do not pre-pay. So removing
`--cover` is **necessary but not sufficient** for a fresh clone: it fixes the
warm steady state, not the first run — and a fresh clone would not reach
`after_doing` anyway, because it must clear `before_doing`'s own 60s budget with
every dependency uncompiled. Tracked as **D229**; it cannot be fixed inside
`after_doing`.

*Under load* is the one that matters day to day, because this file's own
preamble describes two developers on separate clones and a dev server is
normally running. A 1.9× slowdown is an ordinary condition here, not a stress
test, and it puts the section 50s over budget — it takes only ~1.24× to breach.
**A timeout looks exactly like a test failure to whoever reads the result**, so
this is a recurring diagnosis cost, not a one-off. Tracked as **D230**, kept
separate from D229 deliberately: different trigger (contention, not an
uncompiled build), different frequency (recurring, not once per clone), and a
different fix space (budget policy or suite partitioning, not bootstrap
sequencing).

One observation about that load run, stated at the strength the evidence
supports and no higher: `mix test` exited **2** there, on a suite that passes
warm and cold. At the time it did not reproduce, and the failing test was never
captured because the per-command log was overwritten before it could be read.
Recorded then as **one intermittent failure in two loaded runs, cause
unidentified**.

**Since reproduced and identified (D230).** Six loaded runs on an Apple M2
(8 cores, 16 GB) under four CPU burners failed **twice**, and this time every
run's output was retained. Both failures were the same thing, and it is not a
test bug:

```
DBConnection.ConnectionError: could not checkout the connection owned by #PID<...>
... request was dropped from queue after 270ms
    Ecto.Repo.Preloader.fetch_query/8
    Task.Supervised.invoke_mfa/2
```

Ecto's parallel preloader spawns Tasks that each check out a sandbox
connection. Under contention those checkouts queue past DBConnection's default
50ms `queue_target` and the pool begins shedding requests. Both failing runs
still reported **7460/7461 passing** — one spurious failure, no assertion
actually wrong, which is what makes it indistinguishable from a real failure to
whoever reads the gate. Addressed by raising `queue_target` to 500ms in
`config/test.exs`; it was never attributable to dropping `--cover`.

Do not re-add `--cover` here without re-measuring all three states.

## before_doing

```bash
git diff --quiet && git diff --cached --quiet || { echo "Working tree is dirty — commit or stash before claiming a task"; exit 1; }
git checkout main
git pull --rebase origin main || { git rebase --abort 2>/dev/null; echo "pull --rebase conflicted with local unpushed commits — resolve manually"; exit 1; }
mix deps.get
mix hex.outdated || { echo "Outdated dependencies — upgrade before claiming"; exit 1; }
mix deps.audit || { echo "Vulnerable dependencies — patch before claiming"; exit 1; }
mix hex.audit || { echo "Retired dependencies — replace before claiming"; exit 1; }
mix ecto.migrate
git checkout -B "$TASK_IDENTIFIER"
```

## after_doing

```bash
mix test
mix format --check-formatted
mix credo --strict
mix sobelow --config .sobelow-conf
git diff --quiet HEAD -- || (git add -A && git commit -m "Completed task $TASK_IDENTIFIER: $TASK_TITLE")
```

## before_review

```bash
git checkout main
git merge --ff-only "$TASK_IDENTIFIER" || { echo "main moved since branching — ff-only merge of $TASK_IDENTIFIER failed; resolve manually"; exit 1; }
git branch -d "$TASK_IDENTIFIER"
```

## after_goal

```bash
git checkout main
git fetch origin main
git rebase origin/main || { git rebase --abort 2>/dev/null; echo "rebase onto origin/main conflicted — resolve manually, then re-run after_goal"; exit 1; }
mix precommit
git push origin main
```
